# 受控消融实验：薄包装与重复映射构造

日期：2026-09-21。范围：最初候选列表中的 E1–E6；未扩展到算法、缓存、
安全校验、供应商 fallback 或依赖删除。未创建提交。

## 基线与方法

- 最初基线：后端 190 个测试、前端 78 个测试全部通过；Ruff、Vulture、
  TypeScript 与 Vite 构建通过。开始 E2 前保留已接受的 E1，复跑后端 192、
  前端 78 个测试通过。
- 执行路径：FastAPI lifespan → lifecycle → 工作线程内创建 Session →
  scheduler 拉价 → 内存价格更新 → 规则持久化 → Telegram；前端经 API client
  和 Zod 加载并定时刷新。
- 不变量：HTTP 契约、价格与告警输出、数据库事务与查询、Session 清理和线程归属、
  原有异常传播与外部调用策略。
- 逐项执行：补充 characterization tests，先在该因素的原实现上通过，再进行
  单因素修改，执行相关完整测试和静态检查，比较输出及局部性能后接受。
  E5 和 E6 虽然在同一文件中，仍分别修改和验证。
- 性能门槛沿用 E1：局部配对微基准的中位耗时退化不得超过 10%。
  没有现成 benchmark；测试总耗时不作为应用延迟指标。
- 环境：Linux arm64，Python 3.11.2，Node 24.18.1，npm 11.16.0。

## 候选、假设与风险

| 实验 | 组件与假设 | 风险与验证重点 |
| --- | --- | --- |
| E1 | bootstrap 的 Session 工厂只是再次包装 `session_scope`，直接延迟返回即可 | 工作线程、延迟创建、正常/异常清理和异常对象传播 |
| E2 | `formatProviderLabel` 单调用查表可以内联 | 已知标签、未知值回退、空字符串、symbol 原样保留 |
| E3 | `_format_percent_from_ratio` 单调用乘 100 再格式化可以内联 | Decimal 舍入、零值、无阈值、完整转义消息 |
| E4 | `_normalize_query` 单调用 `strip().upper()` 可以内联 | Unicode 空白、空查询不访问供应商、排序与 fallback 不变 |
| E5 | 创建和更新中的新增映射字段清单可共用 | 映射 ID、启用状态、所有供应商、原子回滚、删除清理及额外 SQL |
| E6 | `latest_rule_state_for` 单调用查询可以回收到 `source_status` | 有/无状态、source 隔离、SQL 条件和次数、保留 `require_id` |

## 结果

耗时为对应局部操作的每次调用中位数，不是 HTTP 或线上延迟。
负百分比表示耗时减少，微小差异不视为有意义的提速。

| 实验 | 修改 | 验证结果 | 行为差异 | 原实现 → 消融后耗时 | 生产代码净减少 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| E1 | 删除二次 contextmanager，改为延迟返回原工厂 | 后端 192，前端 78；检查通过 | 生命周期断言一致 | 10.357 → 9.207 μs（−11.11%） | 7 行 | 接受，上一轮完成 |
| E2 | 内联 provider 标签查表 | 前端 84；类型检查、构建通过 | 6 组精确字符串一致，组件 DOM 回归通过 | 0.103930 → 0.103393 μs（−0.52%） | 4 行 | 接受 |
| E3 | 内联百分比换算 | 后端 198；Ruff、Vulture 通过 | 24 条完整消息一致 | 44.825 → 44.743 μs（−0.18%） | 4 行 | 接受 |
| E4 | 内联查询规范化 | 后端 205；Ruff、Vulture 通过 | 8 组查询输出一致；边界测试通过 | 5.354 → 5.332 μs（−0.40%） | 4 行 | 接受 |
| E5 | 将批量添加 helper 改为供两条路径复用的单条添加 helper | 后端 213；Ruff、Vulture 通过 | 创建/更新响应及 11 条 SQL 文本序列一致 | 5,898.139 → 5,887.000 μs（−0.19%） | 8 行 | 接受 |
| E6 | 内联规则状态查询 | 后端 214；Ruff、Vulture 通过 | 有/无状态输出、SQL 文本和参数一致，均一次查询 | 238.575 → 238.696 μs（+0.05%） | 4 行 | 接受 |

E5 没有让创建流程调用同步流程，也没有使用动态字典展开替代显式字段类型。
新增映射只保留一份字段清单；事务和原子回滚逻辑未改动。

## 测量细节

配对实验在同一进程中预热后做 9 轮，交替先运行原实现和新实现，降低顺序偏差。
原模块来自实验开始时 Git HEAD，对照模块来自工作区；没有回退或覆盖工作区文件。
E6 测量的 `source_status` 路径不经过 E5 修改的映射构造，因此对比仍隔离 E6 因素。

| 实验 | 测量范围 | 预热次数/版本 | 每轮次数/版本 |
| --- | --- | --- | --- |
| E1 | 真实 SQLModel Session 的创建/退出，内存 SQLite engine，不执行 SQL | 1,000 | 20,000 |
| E2 | 用项目 TypeScript 编译器转译新旧模块，在 Node 中轮换 6 组标签输入，累加长度避免结果被丢弃 | 100,000 | 500,000 |
| E3 | `format_telegram_alert` 完整消息格式化，阈值 0.02005 | 1,000 | 10,000 |
| E4 | `SymbolCatalog.search`，注入包含 BTCUSDT、WBTCUSDT、ETHUSDT 的固定 Binance 响应 | 1,000 | 20,000 |
| E5 | 内存 SQLite 上创建、更新（保留旧源、添加新源）及删除的完整调用周期 | 10 | 100 |
| E6 | 内存 SQLite 上读取已有规则状态并构造 `source_status` 响应 | 100 | 1,000 |

E1 的 tracemalloc 局部峰值（1,000 次循环）为 2,598 → 2,182 B。
E2–E6 不涉及缓存或长期对象持有，未测服务 RSS，也不声称常驻内存下降。
没有真实外部网络请求、生产负载或跨机器统计；这些微基准不能证明线上速度提升。
计时通过临时 shell 内脚本执行，未添加长期 benchmark 框架或依赖。

## 结论与边界

六个候选均在已执行检查范围内满足接受标准，无失败后扩大修改的情况。
这不证明系统已达到全局最小实现，也不证明未实验的 cache、fallback 或校验可以删除。
尤其保留了真实承担边界职责的 Session 管理、供应商适配、Zod 校验和事务处理。
