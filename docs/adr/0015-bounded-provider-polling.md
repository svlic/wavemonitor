# ADR 0015：为行情供应商请求设置有界等待与隔离

- **状态**：已接受
- **决策时间**：2026-10-16
- **关系**：补充 ADR 0008，不改变单进程调度与内存行情状态的决策。

## 背景

用户报告价格偶发长期不更新。代码检查确认：同步 tick 串行调用供应商，等待请求
完成后才进入下一来源；Hyperliquid Info 未指定 timeout，构造时也会请求元数据。
因此一个不返回的请求能够阻塞后续所有来源和轮次。这是已验证的故障路径，但没有
生产故障时的日志，不能认定它就是本次线上现象的唯一根因。

SDK 的网络超时不能替代整次调用的等待期限：初始化、重试及多次 HTTP 请求会累积。
直接为每次超时启动替代线程则可能积累线程，并并发访问同一 HTTP 客户端。

## 决策

- AdapterRegistry 为每次供应商调用创建 daemon 线程，调度器最多等待 20 秒；只有
  SDK 取价进入该线程，SQLite、规则计算、通知及行情缓存写入仍属于原 tick 线程。
- 每个 Provider 最多保留一个未完成请求。请求超时后，该供应商的后续来源直接记录
  timeout，其他供应商继续轮询；不会每轮创建新的阻塞线程。当前三家供应商最多保留
  三个未完成的行情请求线程，Binance 两种市场共用同一隔离边界。
- 未捕获的适配器异常转换成来源错误，不中断其他来源。
- 超时请求的迟到结果被丢弃，不写入缓存，也不参与规则计算。请求完成后，下一次
  轮询重新获取价格；成功后按既有语义清除来源错误。
- Hyperliquid HTTP connect/read timeout 设为 5 秒，且延迟到首次取价时构造客户端；
  初始化失败按来源错误处理，后续轮询重新尝试构造。
- 保留最后成功价格及其原始时间，错误通过现有 source-errors API 暴露，不将旧价格
  标记为新数据，也不改变 HTTP 契约。

## 结果与权衡

- 单个 SDK 请求无法无限拖住其他供应商的行情更新，故障时后台仍能完成轮次。
- 正常路径仍串行，增加了线程启动成本，但不增加供应商请求频率，不引入新依赖。
- 不能强制终止 Python 线程。永久卡死的供应商会一直降级，需重启后端恢复该供应商；
  其他供应商可继续服务。daemon 线程不会要求进程关闭时等待 SDK 返回。
- 20 秒是单次 SDK 调用的等待期限，不是整轮期限；大量慢请求、SQLite 或通知延迟
  仍可能延长整轮时间。本决策不声称解决所有价格过期原因。

## 替代方案与依据

- 仅增加网络超时：改动小，但 SDK 多步骤调用、锁等待或网络实现异常仍可能阻塞。
- 超时即不断重建线程：可以重试，但无法约束资源占用且可能并发复用客户端，拒绝。
- 可终止的独立工作进程：可恢复永久阻塞，但需要进程生命周期、代理、客户端重建及
  IPC 管理；当前选择局部隔离。若必须无人工干预地恢复永久卡死，再复审进程方案。

## 验证依据

- 调度器回归测试覆盖阻塞供应商的多来源、多轮隔离、其他供应商持续更新、请求数量
  有界、迟到结果丢弃及恢复取价。
- 适配器测试覆盖 Hyperliquid 延迟初始化、初始化失败后的重试及客户端复用；代理
  测试约束构造时的网络超时配置。
