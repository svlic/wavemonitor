# ADR 0013：删除遗留行情观测持久化结构

- **状态**：已接受
- **决策时间**：2026-09

## 背景

初版使用 `PriceObservation` 将每次行情成功结果和供应商错误写入 SQLite，查询 API 从中
选择最新记录，并定期删除三天前的数据。`3f8f100` 依据 ADR 0011 将最新行情和错误迁移到
`LatestPriceStore` 后，运行时不再读写这些记录。

该提交没有同步删除 ORM 模型，因此新数据库仍会创建空的 `priceobservation` 表；SQLite
启动迁移仍为旧表创建索引；删除 Source Mapping 时仍查询旧表；测试则断言该表始终为空。
这些都是 Git diff 和当前代码直接支持的事实。它们是否最初为了兼容旧数据而刻意保留，
历史中没有证据。

项目所有者已要求修复“行情历史持久化被移除，但 `PriceObservation` 结构仍保留”的问题。
ADR 0011 还确认最新行情和 source error 可以在重启时丢失。旧表中的历史行情既不再被产品
读取，也不参与告警状态恢复。

## 决策

- 删除 `PriceObservation` ORM 模型，使新数据库不再创建 `priceobservation` 表。
- 删除 Source Mapping 清理流程中针对该模型的查询，以及旧观测时间索引维护。
- SQLite 启动迁移检测并删除遗留 `priceobservation` 表，包括其中不再受支持的历史行情。
- 保留 AlertEvent、LastRuleState 和 TelegramDelivery 持久化；它们仍承载告警历史、规则状态
  和发送结果，不属于行情快照。
- 暂时保留 API 字段 `observations_written` 以避免契约破坏；其语义继续是本次进程启动后的
  成功内存行情更新次数，而不是数据库写入次数。

## 结果

### 正面影响

- ORM、实际 schema、运行时读写边界和 ADR 0011 保持一致。
- 新库不再创建永久为空的表，旧库也不再为废弃表维护索引或执行级联查询。
- 测试直接验证新 schema 不含该表，并验证旧库迁移可重复执行。

### 负面影响和限制

- 升级旧 SQLite 数据卷会不可逆地删除历史 `priceobservation` 行；需要保留这些数据的部署
  应在升级前自行备份数据库。
- 主数据库不再提供任何历史行情分析或供应商历史稳定性分析能力。未来若恢复此类需求，
  应重新设计保留周期、查询模式和存储成本，而不是复用本次删除的遗留表。
- `observations_written` 的名称仍可能让调用方误解为持久化写入，作为兼容性债务继续保留。

## 已考虑的替代方案

- **只删除 ORM、保留旧表**：可以保住旧行，但不同数据库会长期拥有不同 schema，且无法
  真正完成持久化边界迁移，未采用。
- **将旧表改名或标记为 archive**：仍需长期维护无人读取的数据和迁移规则，未采用。
- **迁移到独立历史行情存储**：当前没有历史行情产品需求，也没有容量、查询和成本要求，
  证据不足，不在本次引入。
- **同时重命名 `observations_written`**：会造成不必要的 HTTP 契约破坏；当前契约已经明确
  其兼容语义，未采用。

## 历史依据

- `509e631`：初版引入 `PriceObservation` 持久化模型和轮询写入。
- `dd3bd86`：增加三天保留期清理，证明该表曾实际承载连续行情记录。
- `b1a145e`、`a5c5f75`：增加并迁移观测时间索引。
- `3f8f100`：停止持久化和查询行情观测，改用进程内 `LatestPriceStore`，但遗留结构未删除。
- `25cfa44`：明确 `observations_written` 的兼容语义以及重启后的空状态。
- 项目所有者确认：可接受重启后丢失最新行情状态，并要求完整移除遗留结构。
