# ADR 0007：使用持久化状态机定义告警与重试

- **状态**：已接受（实现待对齐）
- **决策时间**：2026-06 至 2026-09

## 背景

轮询会反复观察同一条件。如果每次命中都发送 Telegram，会产生告警风暴；如果只按
数据库唯一键永久去重，又会阻止条件恢复后再次触发。Instrument 规则编辑还会使旧的
价格和状态不再适用于新配置。

早期方案曾混合条件边沿和 cooldown 重发，后续又尝试过“每个 source/rule 只发送
一次”和 AlertEvent 唯一约束。历史缺陷证明，告警去重必须由业务状态转换定义，不能
只依赖时间窗口或事件表唯一键。

## 决策

- 每个 Instrument/Source Mapping 持久化一份 `LastRuleState`。
- 一般告警仅在条件进入有效状态时发出；条件失效后清除对应发送标记，以便重新进入时
  re-arm。
- Telegram 发送失败的业务事件应重试，而不是等待下一次条件变化。完成实现对齐后，
  只有成功发送才应完成对应告警的发送标记。
- 规则字段变化时启动新的 `rule_cycle_started_at`，清除旧规则状态，并使历史 crossing
  标记只在当前 cycle 内生效。
- 名称、启停状态或仅 Source Mapping 的变化不启动新 rule cycle。
- AlertEvent 用于保存历史事实，不再以永久唯一约束阻止 reset 后重新触发。
- near-support 在持续接近支撑时，每进入更近的一个整数百分点区间可再次告警；离开
  阈值后重置分档。
- 当前业务边界为：
  - 价格严格低于支撑才触发 support breach；
  - 首次成功观测已经高于阻力也可触发 breakout；
  - 持续停留在相同状态不得重复发送。

项目所有者确认当前业务边界是预期规则，并且不要求多实例下的 exactly-once 保证。

## 结果

### 正面影响

- 服务重启后仍保留告警去重和 re-arm 状态。
- 配置编辑不会继续使用旧规则的状态和 crossing 结果。
- 目标语义允许发送失败后恢复，不会因为先写入历史事件而永久丢失通知。

### 负面影响和限制

- 状态字段、事件历史和发送结果之间存在较复杂的一致性要求。
- 当前保证以单进程、单调度器为边界；多实例可能并发评估同一 source。
- 百分点分档是产品特定语义，不能视为通用告警框架。

## 当前实现偏差

当前代码在规则评估时先持久化 AlertEvent 和 `last_alert_at`，之后才尝试 Telegram 发送。
发送失败不会重新打开该状态；`test_failed_telegram_delivery_does_not_repeat_alert_next_tick`
还明确断言失败会消耗本次告警。因此，当前实现与项目所有者确认的“发送失败应重试”
决策相反。

在实现对齐前，不得把失败重试描述为现有运行时保证。修复时需要同时定义重试上限、
退避策略、重启后的待发送事件来源，以及如何避免成功发送后的重复通知。

## 被替代的方案

- **Cooldown 后重复发送**：被条件边沿语义替代。
- **每个 source/rule 永久只发送一次**：无法在条件恢复后 re-arm。
- **AlertEvent cycle 唯一约束作为最终去重机制**：因阻止同一 cycle 内 reset 后重发而移除。

## 历史依据

- `6916787`、`d1e258d`：从 cooldown 调整为首次条件边沿。
- `25dfd66`：一度采用每 source/rule 一次的发送规则。
- `ab5e037`、`8a144e0`：加入 support breach，并曾加入失败后 re-arm helper。
- `d530a65`：引入数据库告警 claim。
- `0a763e2`、`2c27395`、`6a2d1cc`：加入 rule cycle 和并发编辑保护。
- `4a1a2d6`：移除阻止 reset 后重发的 AlertEvent 唯一约束。
- `c9364b7`：确定当前支撑、突破和 near-support 分档语义。
- `4e36a2f`：删除未接入运行路径的失败 re-arm helper；当前测试随后锁定失败不重发。
- 项目所有者确认：期望的最终语义是 Telegram 失败后重试。
