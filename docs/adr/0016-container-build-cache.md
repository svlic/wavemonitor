# ADR 0016：分离容器依赖层并复用构建缓存

- **状态**：已接受（部署端构建方式由 ADR 0017 取代，缓存策略保留）
- **决策时间**：2026-10-18
- **关系**：补充 ADR 0001，不改变容器运行方式与服务边界。

后续 [ADR 0017](0017-ghcr-multiarch-images.md) 将默认构建位置迁移到 GitHub Actions，
部署端改为拉取 GHCR 镜像；本记录保留当时背景与依赖分层、BuildKit 缓存决策。

## 背景

用户报告构建时 CPU 占用高、耗时长。截图显示前端 build 与后端 pip install
同时执行约 188 秒，但不能据此区分 CPU、网络和内存瓶颈。
代码确认后端先复制全部 backend 再安装依赖，源码或测试变化都会使依赖安装层失效，
且 pip 禁用了下载缓存。前端已按锁文件分层安装依赖。

## 决策

- 保留现有基础镜像、pip/npm 和前端类型检查，不引入新包管理器或跳过检查。
- 从 pyproject.toml 的 project.dependencies 直接生成临时安装清单，不维护重复清单。
  后端先安装第三方依赖，再复制 backend/src 并以 --no-deps 安装应用，执行 pip check。
- 使用 BuildKit cache mount 保存 pip/npm 下载缓存；npm 安装不执行审计和资助提示。
- 根构建上下文排除 Git 和 Amp 工作数据；后端测试不进入运行镜像。
- 文档提供逐服务构建命令，供低配置机器避免前后端同时构建。

## 结果与权衡

源码更新可复用第三方依赖层；依赖变化仍需解析和安装，但可复用已下载的包。
缓存占用额外磁盘，清理后需重新下载；首次构建与前端编译仍有成本。
串行构建只降低服务间竞争，不限制单个工具的 CPU，也不保证缩短总耗时。
依赖仍使用现有版本范围；缓存不是依赖锁定或安全更新策略。

## 替代方案与依据

- 跳过 TypeScript 检查：会降低构建校验标准，不采用。
- 更换包管理器或预构建镜像发布：引入额外维护与发布流程，本次先修复已有缓存边界。
- 全局强制串行或限 CPU：可能拖慢高配置机器，保留为操作者按环境选择。

## 验证边界

本次执行环境没有 Docker，无法测量镜像冷/热构建时间或验证实际 BuildKit 缓存命中。
本地前端测试、构建及后端包安装校验只能验证构建输入，不替代目标机器上的镜像构建。
