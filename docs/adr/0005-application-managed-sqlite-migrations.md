# ADR 0005：由应用启动流程管理 SQLite 迁移

- **状态**：已接受
- **决策时间**：2026-07-06

## 背景

初版只调用 `SQLModel.metadata.create_all()`。该操作可以创建新表，但不能修改已有
Docker 数据卷中的列约束、唯一键或数据表示。项目随后需要将必填 level 改为可空、
修改 Source Mapping 唯一键，并持续增加规则状态字段。

Git 历史没有记录对 Alembic 或其他迁移框架的正式评估。以下关于降低部署步骤的考虑
属于历史推断，而非已确认的原始理由。

## 决策

- 应用启动时先执行 `create_all()`，然后仅对 SQLite 检查已知旧 schema。
- 简单新增列使用 `ALTER TABLE`。
- SQLite 无法原地完成的约束或列变更使用“创建新表、复制转换数据、删除旧表、重命名”
  的方式迁移。
- 每种受支持的旧结构都通过回归测试锁定。
- 迁移必须保留既有 Instrument、映射、规则状态和告警历史。

## 结果

### 正面影响

- 单容器启动即可升级旧数据卷，不需要额外迁移命令。
- 可以对 SQLite 特有的表重建和 JSON 转换进行精确控制。
- 测试能够直接构造遗留 schema 验证升级行为。

### 负面影响和限制

- 迁移没有独立版本号，依赖对表结构的特征检测。
- `db.py` 同时承担连接、建表和多代迁移，复杂度持续增加。
- 路径只针对 SQLite，不构成通用 SQL 数据库迁移方案。
- 未经过历史测试覆盖的中间 schema 可能无法安全升级。

## 已考虑的替代方案

- **只使用 `create_all()`**：无法升级旧卷，已被放弃。
- **Alembic 或其他版本化迁移框架**：历史中没有评估记录。

## 后续复审条件

当迁移分支继续增长、需要支持更多旧版本、引入第二种数据库，或出现无法可靠识别的
中间 schema 时，应迁移到有版本号的迁移工具。

## 历史依据

- `934c356`：首次增加启动时 SQLite 表重建迁移。
- `a5c5f75`：迁移 support breach 状态和观测索引。
- `38c4c52`：将条件阈值迁移为 nullable。
- `110e042`：迁移 rule cycle 和告警 claim 结构。
- `e7732b9`：增加固定回撤字段迁移。
- `2a2f3b5`：将标量支撑阻力迁移为 JSON 数组。
